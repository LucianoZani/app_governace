Governança Unity Catalog

Um app onde usuários de negócio comentam e classificam colunas do Unity Catalog — e a decisão de design que faz isso ser seguro: quando a ação roda com a identidade do próprio usuário, e quando roda com a identidade do robô.

01

Visão geral

É um app Streamlit (não AppKit) de um módulo só: usuários de negócio navegam catálogo → schema → tabela → coluna e aplicam comentários e tags governadas do Unity Catalog. Diferente dos apps AppKit do time, não usa Lakebase, Volumes ou Model Serving — fala só com SQL Warehouse e duas APIs de identidade/governança. Deploy é manual (databricks apps deploy), de propósito fora do Asset Bundle e da pasta que a pipeline de PROD limpa a cada execução.

02

Identidade: quando é você, quando é o robô

Essa é a decisão de design que sustenta o app inteiro. A regra, tal como está no código (função get_client(prefer_user), chamada em cada operação):

O portão de acesso na frente da única escrita como SP

Como ninguém tem MODIFY, comentar só é seguro se o app checar, com o token do próprio usuário, se aquele objeto aparece no information_schema dele — ou seja, se ele já teria pelo menos USE/SELECT. Qualquer exceção é tratada como acesso negado (fail-closed): não existe caminho de "erro = permite".

03

O que acontece quando você edita uma coluna

Do clique em "Salvar e Aplicar Governança" até o log de auditoria — 8 passos, cada um com sua própria identidade (a cor da barra à esquerda), incluindo o desvio de bloqueio do portão de acesso.

04

Isolamento DEV/PROD

Duas instâncias completamente separadas do app (SPs, warehouses e URLs diferentes) apontando para o mesmo metastore. O filtro que você vê na tela (nomes de schema terminando em _dev) é só conveniência visual — o limite real são os grants de cada service principal.

Papéis (RBAC dos cadastros)

Controla só o menu e a edição de cadastros/logs — não tem efeito nenhum sobre quem pode comentar/tagueiar dados de negócio (aquilo é grant de UC + o portão de acesso, seção 02). Usuário sem registro em permissoes entra como leitor por padrão.

● admin — vê e edita tudo, único que gerencia Usuários & Permissões ● editor — edita cadastros, se ver_cadastros=true ● leitor — padrão, somente leitura

O que esse app não usa

Ao contrário dos apps AppKit do time (ex: rag-pdf-files), este não tem Lakebase, Volumes nem Model Serving — é Streamlit puro sobre o databricks-sdk, e todo o estado próprio vive em tabelas Delta comuns.

07

Notas e observações

Duas coisas que valem registrar para quem for mexer nesse app ou usá-lo em produção.

README e guia de uso descrevem a escrita de tags errado

README.md e docs/07-guia-de-uso.md afirmam que tags são escritas pelo service principal. O código faz o oposto: tags rodam prefer_user=True (OBO) em apply_changes() — só o comentário roda como SP. O docstring do módulo e docs/02-arquitetura.md/docs/04-permissoes.md estão corretos e batem com o código; README e o guia de uso ficaram desatualizados desde que o invariante OBO/SP foi formalizado (commit 924c7034).

Governança feita só em DEV não dura

O job de sincronização semanal (Fig. 4) sobrescreve comentários e tags em DEV com o que estiver em PROD. Documentação feita na instância DEV é, por design, efêmera — para durar, precisa ser feita na instância PROD.

Domínios/sub-domínios/stewards são só registro, não trava nada

Nenhum código de apply_changes/apply_table_comment/escrita de tag consulta dominios, subdominios ou data_stewards. A atribuição de steward é informativa — hoje não impede nem libera nenhuma edição; quem decide isso continua sendo o grant de UC (tags) e o portão de acesso (comentário).
